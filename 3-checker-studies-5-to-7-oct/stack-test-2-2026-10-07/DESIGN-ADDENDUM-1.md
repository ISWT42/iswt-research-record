## 2. What differs from the plan, and why (clarifications the sealed files left open)

1. **The broker cannot send S12's body.** Checked in `ai-broker/lib`: `openrouter` sends `reasoning: {enabled: true}` with no effort and no temperature or seed; `openrouter-plain` sends reasoning off, temperature 0, seed 42 and `max_tokens` 400 (`openrouter-plain-long`: 1200); and `planModel` refuses `--effort` for every provider except codex and claude. A private config copy (the one the cross-model panels use, `maxOutputTokens` 6000) changes only `max_tokens` and cannot add the effort. So `run_matrix.py setup-broker` builds a **private copy of the broker's code** in `broker-copy/` (35 files; manifest `broker-copy/COPY-SHA256.txt` lists the copied files and the git HEAD it came from), adds one adapter, `lib/providers/openrouter-matrix.mjs` (source in `broker-adapter/`), and registers it in two files. The real broker is not touched. The adapter writes the exact request it sent into the ledger's `raw.json` as `request_sent`: that record is the proof. The copy reads its configuration (key names, confidential markers, provider terms) from the real broker's folder and its keys from the same DPAPI key store, and writes a **private ledger** in `ledger-matrix/` (hash-chained by the same code; `results/ledger-heads.txt` gets its `index.head` and a `verify` line before and after every ours run). To use the real ledger instead, install the adapter in the real broker and set `ours.broker_copy`, `ours.broker_source` and `ours.ledger_dir` in `SETTINGS.json`; the runner is otherwise unchanged.
2. **Reader.** The scored rule is the coat-check screen's `read` in `score_screen.py`, unchanged and checked against the screen's seal (`ADDENDUM-1-SHA256.txt`), with the entry's `cvp/scorer.py` checked against `SCORER-SHA256.txt`. `matrix_reader.py` is a box-safe mirror used only by the runner's pause rule; `score_matrix.py` stops if the mirror ever disagrees with the screen's `read`. The audit rule (S10) is `matrix_reader.read_reference`: the same parse, then the last complete JSON object holding the version's field, found with `json.JSONDecoder.raw_decode`. Planted replies on which the two rules differ (the sealed rule stays the scored one; S10 prints these): two objects, two identical objects, a stray closing brace after the object, a stray opening brace before the object, and a reply that is a JSON array holding the object. Every other planted case (braces inside strings, a quote that is itself JSON, a field named verdict or status inside the evidence, a fenced reply, a think block, a reply cut off, prose around one object) reads the same under both. If the coordinator wants the reference rule scored instead, that is a change to `score_matrix.py` and must happen before the run seal.
3. **Codex tool items.** DESIGN-A counts any item whose type is not `agent_message` or `reasoning`. The runner also leaves out items of type `error` (the tool reporting an error, not a tool request); they are recorded with the diagnostic text and can end a call as an error. Refused means the item's status is declined, failed, error, rejected, denied or blocked and nothing ran (no exit code, no output); anything else, and any unknown item type, counts as executed and halts the cell.
4. **Claude Code tool items.** Every `tool_use` block is an attempt. Refused: its `tool_result` is an error whose text reads as a refusal (no such tool, not allowed, permission, denied, disabled, blocked, and similar) or its id is in the result event's `permission_denials`. Executed: any other result, or no result at all (conservative: it halts the cell).
5. **Plan-limit and login messages** are read from error text only (stderr, an error result, Codex `error` and `turn.failed` events), never from a model's reply. A plan-limit message, a login failure, a refused gate, HTTP 401, 402 or 403, an executed tool, a changed tool version, a changed route-reported model id, a non-empty working folder after a call, and a request body that differs from the sealed one each stop the cell with `results/<cell>-w<wave>.STOPPED.json`; the call that met the message is not recorded, so a resume repeats it. "Pause and ask" (more than half of the first 96 calls of a CLI cell invalid; three or more calls answered by another model) writes `PAUSE-<cell>` containing the reason, and the cell waits until the file is deleted or `HALT-<cell>` is written.
6. **Model identity.** Ours: the response's `model`. Claude Code: the model on the last assistant message (the init event and `modelUsage` are recorded; small-model helper calls in `modelUsage` are recorded, not flagged). Codex: the `model:` line of the stderr header if it appears with `--json`; if it does not, nothing is reported and the flags as passed are the record (**PROBE** says which).
7. **Reading rules in code.** R1: a repeat is complete with all 192 rows; a cell with fewer than three complete repeats is read on repeat 1 alone in every comparison (both cells), labelled "one run"; `--count-missing-as-invalid` instead reads every started repeat and counts a row that is missing as an invalid run, reported (an exploratory label belongs on any such read). G2's threshold of 10 extra invalid runs is scaled to 4 when only one run is read. R5: P1 and P2 (and S1, S2, S6, S7) need the ours twin on the same UTC date as the theirs cell; P3 may span two dates and prints the dates and a caveat. R6: a cell with an executed tool, two tool versions or two route-reported model ids is reported alone and left out of every test. A run row whose status is "no answer" or whose model differs from the asked one is an invalid run; a cut-off reply (finish reason `length`, or Claude Code's `max_tokens` stop) is no answer. Codex gives no cut-off signal: a truncated Codex reply is read, fails to parse, and scores as invalid.
8. **Forecasts.** A statement needing a cell, or three complete repeats (A14, A15, A20), or all seven primaries (A22), or a second ours run (A21) prints "not run" until it has them; A8, A13, A18 and A19 need all four cells.
9. **The probe in the box and the seal.** `box_start.sh` runs the runner's `check`, then `probe` (version, `auth status` or `login status`, the three canaries with exact sentinels and zero tool items, two toy calls, the knob check), and starts the cell only if the probe passes; it writes `results/probe/<cell>-PASS.json` (settings hash, version, dropped flags), which `run` requires (valid 12 hours). `RUN-SHA256.txt` must be written by the coordinator, must list every file the box needs (the runner stages exactly the listed files with `stage_to_box.sh`), and the runner and scorer refuse to run without it. `results/probe/PROBE-REPORT.md` is regenerated by every probe; the coordinator copies the final one next to this addendum before sealing.
